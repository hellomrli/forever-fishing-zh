# 持续优化与上游采用记录

## 2026-11-25：简化钓鱼流程

当前源码改为 Python v1.1.0 / Rust 2.0.0-alpha.3：监控金色齿轮，咬钩声音命中立即起杆，默认 30 秒无咬钩声音直接重抛。移除水花画面确认、候选等待、反应延迟与跳过咬钩；开始或恢复时已有齿轮就继续等待。图标丢失防抖为 1 秒，覆盖 20 毫秒音频批次下的声音识别延迟。

已重新核对 GitHub API 和参考仓库的 `origin/main`，上游最新提交仍是 `97653ba0566d2e1c14b70848888c76f674f7655e`，没有新增待评审提交。保留落水等待、图标尺度与金色过滤、客户端 PID 音频选择及窗口身份刷新；此前排除已有齿轮的规则改为接着等待。

发布前的 Windows CI 暴露了配置并发保存超时：8 个线程各更新 10 次时，等待本进程其他写入也占用了 5 秒文件锁期限。Rust 改为先串行化同一进程的保存，再计算跨进程锁的 5 秒重试期限；回归使用独立创建的 Store 访问同一文件，验证 80 次更新均保留。

Python 114 项、Rust 44 项 release 回归通过；Ruff、Rust 格式、Linux / Windows MSVC 目标严格 Clippy 与 Linux release 构建通过。两版实际界面自检覆盖 900×640 及三档字体缩放，验证记录见 [简化钓鱼验证](audit/simple-fishing-validation.json)。

动作规则、30 秒计时、配置兼容与验证范围见 [简化钓鱼设计](简化钓鱼设计.md)。以下为上一轮历史采用记录。

## 上游跟踪

基线位于 [`.github/upstream.json`](../.github/upstream.json)。运行：

```bash
python3 scripts/check_upstream.py --fail-on-changes
```

脚本先解析上游分支的固定提交，再生成提交和文件差异，写入 `checks/upstream/upstream.json` 与 `upstream.md`。已评审到最新提交时返回 0；有未评审变化时返回 1；网络、基线或报告写入失败时返回 2。当前基线与上游一致的路径已实测返回 0；使用原基线的临时副本，实测返回 1 并报告 36 个提交、52 个文件。

[`Upstream Review`](../.github/workflows/upstream.yml) 在默认分支每日 UTC 02:30（北京时间 10:30）检查，并上传可审阅报告；合入默认分支后定时生效，也可手动在目标分支执行。完成采用记录与验证后再更新评审提交。报告保留固定差异链接，较长列表可能受 GitHub 比较接口的返回上限影响。
